# 找个搭子 · 每日用户模拟反馈循环

每天固定时间拉起一批子代理，让他们从真实用户的视角体验产品，把反馈交给
固定开发团队，团队当天做小幅优化。目标：产品每天都比昨天好用一点。

## 每天的人员构成（固定）

- **长期用户 3 名**（身份固定，带记忆）：见 `users/longterm/`。
  每天同一批人，读自己的 journal 再继续用，像真老用户一样积累体验。
- **新用户 3 名**（每天换人、换角度）：从 `new-user-angles.md` 里按顺序取
  3 个未用过的角度，每天现场生成身份，首日体验（注册/登录、逛大厅、报名、
  发布），给新鲜视角的建议。角度两周内不重复。账号用固定临时池 temp01–
  temp03（每天重置复用，见 RUNBOOK 第 2 步），不每天新起名；长期用户一直
  用 organizer/demo01/demo05。
- **开发团队 4 名**（长期不变）：见 `TEAM.md`。产品经理 1、后端 1、前端 1、
  测试 1，每天同一套人设和工作约定；每人开工前先读 TEAM.md「能力配置」
  里自己名下的 skill（项目专属的新建 skill 在
  `~/workspace/custom-skills/campus-buddy-backend/` 与 `campus-buddy-qa/`）。

每天最多 9 个子代理：6 个用户 + 产品经理 + 2 名开发 + 测试（测试可与产品经理
先后串行，不必并行拉满）。

## 每天的流程（细则见 RUNBOOK.md）

1. 环境恢复：虚拟机可能被重置，先按既定流程从备份恢复库、启动后端并验健康。
2. 数据库快照：用户体验开始前 `pg_dump` 一份当日快照。
3. 用户体验（并行）：6 名用户各按人设和场景，用 Playwright 驱动
   http://127.0.0.1:8080 操作产品并截图，各写一份反馈报告到
   `runs/YYYY-MM-DD/users/<名字>.md`。
4. 产品经理汇总：去重、定优先级（P0/P1/P2），写 `runs/YYYY-MM-DD/digest.md`。
5. 开发优化：后端 + 前端按优先级做最多 3 项小改动，改动记入
   `runs/YYYY-MM-DD/changes.md`；测试跑通后端测试与移动端测试、复核数据库
   不变量后才算完成。
6. 恢复数据库：用步骤 2 的快照恢复，当天用户体验产生的数据不留库。
7. 交付：当天的 `digest.md` 摘要发到用户所在的 side chat，完整报告留档。

## 不可违反的规矩

- 数据库第一：任何用户代理绝不点「恢复演示数据」；当天体验数据事后必恢复。
- 改动要小、可逆、有测试；数据库结构改动只许提议，不许当天擅自实施。
- 反馈要诚实：没复现的问题写没复现，没改完的写没改完，不许把没做的说成做了。
- 长期用户的 journal、开发团队的 TEAM.md、新用户角度清单是长期资产，
  每天只追加、不重写、不换人。
